# Server-Side Search & Filter — Implementation Plan

## Problem
1. **Timeout bug**: `searchAllUnits()` makes 2-3 sequential HTTP requests (units query + allotments query with fallback). On a slow LAN, the allotments query with `expand: 'allottee, unit'` + 11 `~` OR-clauses can exceed the 12s per-request timeout.
2. **Feature request**: New dedicated search/filter screen with separate fields for Type/Category, House No, CNIC, Allottee Name, Personal No, AND logic, Search/Clear buttons, and results grouped by unit → allotment → payment records.

## Design

### 1. Fix existing global search timeout
**File: `lib/repositories/units_repository.dart`**
- Increase `requestTimeout` in `pocketbase_service.dart` from 12s to 20s — the allotments query with expand and 11 OR-clauses is genuinely heavy on a slow LAN.
- Remove the `_searchAllotments` fallback pattern (the `personal_no`/`phone` fields now exist on the server). Replace with a single query, removing the try/fallback which doubles worst-case wall-clock time.

### 2. New `searchFilteredUnits()` repository method
**File: `lib/repositories/units_repository.dart`**

A new method that builds a single PocketBase filter from the provided fields using AND logic. Only non-empty fields are included.

**Filter construction:**
```
type ~ {:type} && house_no ~ {:houseNo} && 
(unit.allottee.name ~ {:name} || unit.allottee.cnic ~ {:cnic} || unit.allottee.personal_no ~ {:personalNo})
```

This requires querying the **allotments** collection (with `expand: 'allottee, unit'`) because allottee fields live on a separate relation. For a vacant unit that has no allotment record, a separate units query with the Type/HouseNo filter is needed.

**Two parallel requests:**
1. **Allotments query**: `date_of_vacancy = '' && <unit/allottee filter clauses>` — finds allotted units matching any field
2. **Vacant units query** (only if allottee fields are empty): `type ~ {:type} && house_no ~ {:houseNo}` with a subsequent check that the unit has no active allotment — finds vacant units matching unit fields only

Results are merged by unit ID, deduped, and returned as a list.

**A new model class `SearchResultItem`** (in `lib/models/search_result_item.dart`):
```dart
class SearchResultItem {
  final UnitModel unit;
  final AllotmentModel? activeAllotment;
  final AllotteeModel? allottee;
  // Payments loaded lazily on expand
}
```

### 3. New `SearchScreen`
**File: `lib/screens/search_screen.dart`**

Full-screen route pushed from a search icon in the AppBar.

**Layout:**
```
AppBar: "Search & Filter" with search icon
Body: SingleChildScrollView
  └─ Column
     ├─ 5 filter fields (TextFormFields):
     │   ├─ Type/Category
     │   ├─ House No.
     │   ├─ CNIC
     │   ├─ Allottee Name
     │   └─ Personal No.
     ├─ SizedBox(height: 16)
     ├─ Row: [Search button (Expanded)] [Clear Filters (OutlinedButton)]
     ├─ SizedBox(height: 16)
     └─ Results section:
        ├─ LoadingView (while searching)
        ├─ ErrorRetryView (on error)
        ├─ EmptyStateView (no results)
        └─ ListView of expandable result cards
```

**Each result card** is an expandable `Card`:
- **Collapsed**: Shows unit label (`displayLabel`), colony · type, allottee name
- **Expanded** (on tap): Shows full unit info rows, allottee info rows, and a `PaymentList` widget for that allotment's payment history (uses the existing `PaymentList` with its `loadPage` callback calling `PaymentsRepository.getHistoryForAllotment()`)

This matches the existing `AllottedUnitView` pattern but in a compact, expandable card format suitable for a search results list.
