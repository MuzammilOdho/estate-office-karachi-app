## Phase 1 — Critical (blocks core scaling failure + concurrent-user correctness)

### 1a. Rewrite global search — eliminate the full-table scans [C1+C2]
**File:** `lib/repositories/units_repository.dart`

- Replace `searchAllUnits(query)` body. New approach: **two bounded `getList` calls**, no full-table fetch:
  1. **Units by unit fields** — `getList(perPage: 200)` on `units`, filter = `house_no ~ {:q} || block ~ {:q} || flat_no ~ {:q} || colony ~ {:q} || type ~ {:q}`, via `_pb.filter(...)`.
  2. **Allotments by any field** (covers allottee name/cnic/designation/department AND the unit fields, since they're reachable via the `unit` relation) — `getList(perPage: 200)` on `allotments`, `filter: 'date_of_vacancy = ""' && (unit.house_no ~ {:q} || unit.block ~ {:q} || unit.flat_no ~ {:q} || unit.colony ~ {:q} || unit.type ~ {:q} || allottee.name ~ {:q} || allottee.cnic ~ {:q} || allottee.designation ~ {:q} || allottee.department ~ {:q})`, `expand: 'allottee, unit'`.
  3. Build `UnitListItem` rows from both result sets, **union by unit id**, then run the **existing** `_matchScore` + `_compareUnits` ranking on just the union (tens of rows, not 10k).
- Delete `_joinWithActiveAllotments` (no longer used — its job is done by call #2's `expand`).
- `getUnitsForColonyAndType` — keep its server-side `colony && type` filter (already correct) but swap its `_joinWithActiveAllotments(unitRecords)` call for a **scoped** active-allotment query: `getList` on `allotments`, `filter: 'date_of_vacancy = "" && unit ?= {:ids}'`, `expand: 'allottee'`, passing the fetched unit ids. Reuses the same local map-build that `_joinWithActiveAllotments` already does inline — extract the map-building lines into a small private helper so both call sites share it.
- Keep `_matchScore`, `_compareUnits`, `naturalCompare` import — all still load-bearing for sort/rank correctness.
- Add `fields` projection to `getColonies`/`getTypesForColony` (already present) — no change.
- **Min query length stays at 2 chars** (`colonies_screen.dart:84`-adjacent behavior preserved); `perPage: 200` cap is a sane ceiling for search results (matches audit log's existing pattern at `audit_log_repository.dart:38`).

### 1b. Allotment uniqueness — backend snippet only [H3]
- **No client change** in Phase 1 (the client check-then-create stays as a friendly fast-fail — removing it would degrade UX).
- **Deliverable:** a backend snippet (JS `beforeCreate`/`beforeUpdate` hook + the index) handed to you as text. The client can't enforce this; it's the server's job.

## Phase 2 — High-impact (reliability + the payment long tail + backend indexes)

### 2a. Paginate payment history — auto-load on scroll [H1]
**Files:** `lib/repositories/payments_repository.dart`, `lib/screens/unit_detail_sheet.dart`, `lib/widgets/allotted_unit_view.dart`, `lib/screens/allotment_detail_screen.dart`

- `PaymentsRepository`: change `getHistoryForAllotment` → `getHistoryForAllotment(allotmentId, {int page = 1, int perPage = 50})`, switch `getFullList` → `getList(page, perPage, sort: '-date', expand: 'created_by')`, return a `(List<PaymentModel> items, int totalItems, int totalPages)` result (use a small `PagedResult<T>` in the repo, or return the SDK `ResultList<RecordModel>` and map in the caller — pick the simpler of the two at implementation time).
- `UnitDetailSheet`: fetch first page only in `_load()`. Pass the partial list + a "load more" callback down to `AllottedUnitView`.
- `AllottedUnitView`: render payment tiles in a `ScrollController`; when the user scrolls near the bottom and more pages exist, call the callback to fetch the next page and `setState`-append. Show a small loading indicator while fetching, "No more payments" when exhausted. **Preserves** the "I can scroll all history" feel — just faster first paint.
- `AllotmentDetailScreen` (`_PaymentTile` list): apply the same paged/scroll pattern. Its payment tiles are a duplicated widget (`_PaymentTile`) — consolidate the two identical `_PaymentTile` definitions into one shared widget (see Phase 3) as part of this change to avoid diverging them again.
- Add a `perPage: 50` constant in `payments_repository.dart`.

### 2b. Stream export CSV incrementally [H1 / M3]
**Files:** `lib/repositories/export_repository.dart`, `lib/utils/csv_export.dart`

- `ExportRepository.buildReport(...)`: stop returning `List<ExportRow>`. Instead expose a `Stream<ExportRow>` (or a `Future` that writes to a provided `StringSink`). Fetch payment pages from the server via `getList(page, perPage, sort: '-date')` loop (already sorted -date by the server — **drop the redundant client re-sort** at `export_repository.dart:160`). For each page, resolve the small distinct-allotment set via the existing approach **but prefer `expand: 'allotment.allottee, allotment.unit'` on the payments query** to eliminate the OR-id filter (M3) when practical; keep the OR-id fallback only if the expand proves too large.
- `CsvExport`: convert `buildCsv(List<ExportRow>)` → `buildCsv(Stream<ExportRow>, {int? rowCountHint})` that writes the header, then each row's cells as it arrives, into the temp file via a `StringSink`/file handle. `shareCsv` then shares the file as today. No full `List<ExportRow>` and no full CSV string materialized — memory stays at ~1 page regardless of export size.
- **UX preserved:** the `ExportScreen` still calls a single `generateAndShare` method and reports `rows.length`; we carry a running count through the stream so `_lastRowCount` still works (`export_screen.dart:171`).
- Handle the streaming edge cases: empty result (existing early return), orphaned payment (existing `continue` at `export_repository.dart:123`), missing `expand` records (existing `continue` at `:129`).

### 2c. Request timeouts — fail fast to the retry view [M6]
**Files:** `lib/services/pocketbase_service.dart`, `lib/utils/app_exception.dart`

- In `PocketBaseService`, expose a shared `Duration requestTimeout = const Duration(seconds: 12)` (LAN-appropriate).
- Add a `TimeoutException`-to-`AppException` branch in `asAppException` (`app_exception.dart`) so timeouts render the **existing** friendly "Can't reach the server" message instead of a stack trace.
- Add a thin helper in the repo base pattern (e.g. a private `_guarded<T>(Future<T> Function() op)` wrapper that does `op().timeout(requestTimeout).catchError(asAppException)`) and wrap the ~12 `getFullList`/`getList`/`create`/`update` calls. Keeps per-call boilerplate to one wrapper and centralizes the timeout.

### 2d. Image decode-sizing [H2a]
**Files (6 sites):** `allotment_detail_screen.dart:204,229`, `allottee_history_screen.dart:195,200`, `allotted_unit_view.dart:257,285`
- Add `cacheWidth: (44 * MediaQuery.devicePixelRatioOf(context)).round()` / `cacheHeight:` matching each `Image.network`'s displayed box (44×44 thumbnails, 64×64 doc thumbs, and the fullscreen `InteractiveViewer` images keep no cache sizing since they're full-size by design). Zero new dependencies.
